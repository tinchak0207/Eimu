# 可复现评测包

目标：任何人用同一份题面、同一个评分器，能把本文的分数**逐位重跑出来**。

## 一条命令

```bash
./install.sh    # 拉 SongBench 官方仓库 + 应用 eval_gpu.patch + 装依赖
./run.sh        # 转 WAV → 评分 → 汇总
```

`run.sh` 用到 `eval/audio/` 里我方交付成品的音频；换掉这个目录即可评自己的曲子。
目录内是 4 首入榜成品的单次版本 + 《逆风不灭》额外 7 个 take（榜单该曲取 best-of-8）+ 1 首纯音乐（排除出榜）。

## 复现口径（缺一项就不构成同口径对比）

| 项 | 值 | 为什么 |
|---|---|---|
| 评分器 | 官方 `eval.py` + `ckpt/songbench.safetensors` + MuQ-large-msd-iter，fp32 | 公式未改，见 `eval_gpu.patch` |
| 输入格式 | **44.1 kHz 立体声 WAV** | 24 kHz 单声道会让七个维度系统性上移，分数不可比 |
| 降内存档 | `--mem_level 1`（长曲用 4，前端搬 CPU） | 两档在正控制曲上逐维等价 |
| 正控制曲 | `media-1789821225748-t6qbpy.wav` → **mean7 = 6.9150** | 先跑它，对不上就别采信后面的数字 |
| 题面 | `prompts/idx0-prompt.json`，435 字符，`sha256 7e462c5c…` | 消融实验四条通道跑的就是这一份 |

## 目录

```
eval_gpu.patch                对官方 eval.py 的差分（含逐项说明）
install.sh / run.sh           环境与跑批
score.py                      把官方逐档输出汇总成七维 + 均分
analysis/asr-lyric-fidelity.py 指令遵循尺：ASR 转写成品 → 对题面歌词算字符级召回
scores/human-canon-27.json    27 首得奖曲：曲名/艺人/奖项/七维/均分（无音频）
scores/eimu-delivered.json    我方交付成品：七维/均分；含 best_of_8_nifeng 与排除记录
scores/arms-paired.json       消融四条通道：逐题面逐 take 明细 + best-of-k
scores/lyric-fidelity.json    消融四臂的歌词保真（ASR 字符召回）
scores/songeval-arms.json     消融四臂的 SongEval 五维（第二把感知尺）
prompts/idx0-prompt.json      题面（含 sha256）
audio/                        我方交付成品音频 + 《逆风不灭》的 8 个 take（可重跑）
```

## 榜首那一行的口径：best-of-8

榜单上《逆风不灭》的 **7.418** 不是单次生成，是**同一句提示词 8 次生成里最好的一首**
（提示词：「我想要一首类似飞儿乐团那种喧闹史诗风格的乐曲」；通道：Beast On Mode +「再来N组」）。

| 口径 | 值 |
|---|---|
| best-of-8（榜单用） | **7.4179**（`nifengbumie8.m4a`） |
| 8 首均值 | 7.0281 |
| 8 首 sd | 0.1749（极差 0.53） |
| 单次版本（take1） | 6.9719 |

为什么要单列出来：**best-of-N 是真实的杠杆，不是话术**。同 prompt 8 个 take 的 sd 是 0.175，
而此前只标定过 n=1 对的 0.059；取 max 相对取 mean 净赚 +0.39。8 首的逐维明细在
`scores/eimu-delivered.json` 的 `best_of_8_nifeng`，8 个音频全部随包提供，可自行重跑核对。
但**拿 best-of-8 与单首人类录音并排是不同筛选强度**，正文与图上都明示了这一点。

## 消融实验：补满样本后的结果

**先看题面是什么**：四臂跑的是 WildSongBench 的 192 条 prompt 之一（逐字节一致，435 字符 /
`sha256 7e462c5c…`），而它是**一份已经写好的成熟 brief**——`[Tags] <风格/人声/语言>` + 逐段带
结构标记的完整歌词。风格、人声、语言、完整歌词、段落结构全部给定。
**因此这次消融把 harness 的「把一句话变成 brief」那一层设成了常量（四臂人手一份），
测的只是执行层。** 下面表里的数字不能读成「harness 没用」。

3 个题面 × 3 take，四条通道：

| 通道 | n | mean7 |
|---|---|---|
| 裸 Lyria（无 harness） | 9 | 6.7063 |
| 裸 YuE2（无 harness） | 9 | 6.5015 |
| Eimu 编排 → FlowMusic | 9 | 6.6926 |
| Eimu 编排 → YuE2 | 7 | 6.5588 |

同题面配对差：**Eimu→FlowMusic − 裸 Lyria = −0.0137**，**Eimu→YuE2 − 裸 YuE2 = −0.0084**；
两条的自助法 95% 区间（−0.128 ~ +0.233）都跨过 0。**结论仅覆盖执行层**：给定同一份成熟 brief，
take 管理／通道降级／交付契约对**单次分数**没有可测增益。（臂 C 的 n=7 是 harvest 来的——
见下方「已知坑位」第 5 条——不是受控样本。）

把手上 3 take 按「取最好的一首」重算，四臂斜率几乎一样，**「多取样取最好」是模型自带的杠杆**：

| 通道 | 3 take 均分 | 3 take 取最好 | 取样收益 |
|---|---|---|---|
| 裸 Lyria（无 harness） | 6.7063 | 6.8274 | +0.121 |
| 裸 YuE2（无 harness） | 6.5015 | 6.7029 | +0.201 |
| Eimu 编排 → FlowMusic | 6.6926 | 6.8998 | +0.207 |

harness 在这里的贡献是**把「跑 N 组取最好」做成一键能力并把 N 拉到 8**——榜首 7.418 走的就是同一句
人类提示词 8 次取最好，这是它得以存在的前提。**而「一句话 → 成熟 brief」的导演层这一环本次未测**：
产品主线的对照实验（同一句人类口语提示词，裸臂 vs harness 臂）还没跑，见正文末节。
逐 take 明细见 `scores/arms-paired.json`。

## 换尺：感知尺看不见的那条轴（指令遵循）

SongBench 和 SongEval 都是「听起来好不好」的感知裁判。但题面里**写明了歌词、人声类型、语言**，
产品交付的第一件事是**照着唱**——这不在任何感知尺的量程里。为此加了一把客观尺：
把题面写给模型的歌词当 ground truth，ASR 转写成品，算字符级召回（`analysis/asr-lyric-fidelity.py`，
faster-whisper small，CPU，按题面语言选 zh/en）。

同一批 34 首音频，三把尺：

| 尺 | 量的是什么 | 裸 Lyria | 编排→FlowMusic | 编排→YuE2 | 裸 YuE2 |
|---|---|---|---|---|---|
| SongBench（7 维） | 听起来好不好 | 6.7063 | 6.6926 | 6.5588 | 6.5015 |
| SongEval（5 维，独立第二把） | 听起来好不好 | 4.4488 | 4.3162 | 4.3098 | 4.3768 |
| **歌词保真（ASR 召回）** | **有没有照着题面唱** | **0.308** | **0.580** | **0.641** | **0.721** |

- 感知轴上换尺不改结论：两把独立训练感知裁判同向，编排层净差都在 0 附近。
- 同一批音频在「照着唱」轴上**差 7 倍**（英文题面 idx100：裸 Lyria 0.130，走对通道 0.804 / 0.922），
  而两把感知尺对此**完全失明**。
- 拉开它的**是通道/路由选择**（编排→FlowMusic − 裸 Lyria = +0.273，英语题面 +0.674），
  **不是编排层的生成期干预**（同通道对照 编排→YuE2 − 裸 YuE2 = −0.071）。

逐曲明细见 `scores/lyric-fidelity.json` 与 `scores/songeval-arms.json`。

## 排除记录

《第二遍雨》是**纯音乐**（人声当配器使用）。SongBench 七维里含 Vocal 维，对无主唱作品不适用，
计入会系统性压低该曲均分、把「编排水平」和「有没有主唱」两件事混在一起，故**不入榜**。

排除是**口径判断，不是改分**：它的 6.243 仍是它在这把尺上的真实得分，音频与逐维分数都随包保留
（`scores/eimu-delivered.json` 的 `excluded_from_chart`），任何人都能自己重跑核对。

## 已知坑位

1. **正控制曲对不上，先别信任何数字。** 它是整套比较的锚；四批独立运行都得到 6.9150。
2. **输入格式**：24 kHz 单声道会系统性抬高七维约 +0.1，任何跨格式对比都是错的。
3. **别在同一张卡上同时跑生成与评测**：生成峰值约 7.1–7.4 GB，评测约 5.1 GB，8 GB 卡会 OOM。
4. **bf16 会改数值**：`mem_level 3` 及以上会切 bf16，除非你重做等价性验证，否则别和 fp32 混比。
5. **臂 C（Eimu → YuE2）不是受控样本**：harness 调用本地 YuE2 的客户端超时短于 YuE2 实际出歌时长
   （约 6 分钟），超时后产物被丢弃，缺的 2 首是从 YuE2 的 run 目录 harvest 回来的，所以 n=7 而非 9。
   这是 harness 的**跑通率缺陷**，不是采样噪声——补样本会掩盖它。
6. **歌词保真度这把尺本身有噪声**：whisper-small 转写「唱」的音频本就不如转写「说」的准，
   绝对值不可当真（不要拿 0.72 说「唱对了 72%」）；它的用处是**同一批音频上的相对对比**。
   转写语言必须按题面选（idx100 是英文歌，用 `language=zh` 会把数字全部带偏）。

## 这些分数不是什么

- 裁判是**在 AI 生成音乐上训练的奖励模型**，对真实商业母带属分布外。
- 27 首得奖曲是**未经筛选**的参考集；我方**榜首那一行是 best-of-8**（同一句提示词 8 次生成里最好的一首，
  见上节），其余 3 首为单次交付。两边筛选强度不同，正文与图上均已写明。
- 这是**同一把尺上的相对分数**，不是对音乐价值的判断。
- **消融实验只覆盖执行层**：它把「一句话 → 成熟 brief」的导演层设成了常量发给四臂，所以测出的
  「配对差 −0.014 / −0.008」说明的是执行层对单次分无增益，**不能读成 harness 无用**。产品主线的
  对照实验（同一句人类口语提示词，裸臂 vs harness 臂）尚未跑。
- **感知尺不是全部**：SongBench / SongEval 只量「听起来好不好」。同一批音频在「有没有照着题面唱」
  这条轴上差 7 倍，两把感知尺对此完全失明——评 harness 必须同时看指令遵循与流程指标（见上节）。
