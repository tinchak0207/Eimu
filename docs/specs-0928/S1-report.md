## 結論（先講）

1. **23 把外部 key 裡，14 人從未發起過任何一次生成**（`generation_job` source=biz 零行）。他們不是「被拒」，是**沒按按鈕** —— 建 key 與最後一次登入往往同一分鐘之內（12/14 在 5 分鐘內），屬於註冊會話當下順手簽一把 key 就再也沒回來。
2. 剩下 9 人首單結果：**5 人首單成功**、**4 人首單就退款或拒單**（deadline_exceeded ×2、model_unsupported ×1、billing zombie ×1）。
3. **本輪無法回答「有沒有人打了卻被 401」** —— 被拒請求不進 `generation_job`，改動前的任何日誌都不含 key 身分。這正是 S1 新增 `api_rejection` 要填的洞（本報告只能用「沒有 job」推測「沒發起」，兩者不可區分）。
4. 佐證性事實：23 人 **new-api 消費記錄（type=2）為 0 行**，`top_ups` 全空表 —— 沒有任何一人真正付過錢；4 人的「充值」是兌換碼（ID 209/409/410/412）。
5. 14 個未發起者中 **5 人的 new-api 額度是 0**（245/250/251/252/254），即使他們按了按鈕也會撞 402；另 **9 人額度充足卻沒發起**（其中 124 靠兌換碼有 $1500 等值額度）。

## 與規格／記憶的衝突（現場為準）

1. **`authenticateBizKey` 不存在**。真正的驗證函數是 `authenticateBizApiKey`（`src/lib/biz-api-key-store.ts:461`）；`src/lib/biz-openai-error.ts` 的 `guardBizApiKey` 只服務 `/api/biz/*`，本次未動。spec 用 grep `authenticateBizKey` 找入口會落空。
2. **「16 人一次調用都沒成功過」不精確**。現場：14 人**完全沒發起**；9 人首單成功者 5 人，另 4 人首單失敗。`biz_api_key.total_requests` 亦只有 22、116 兩人不為 0（此計數僅在成功交付時累加）。
3. **87、90 疑為內部探針帳號**（不在 `INTERNAL_USER_IDS=117,82,253` 名單內）：admin 供給型巨額額度（49999994015 / 4999999500，`used_quota=0`）、零登入零簽到、建號當下即簽 key 並立刻出圖、此後消失。本報告**未剔除**（按 spec 名單），但影響所有分組：剔除 87/90 後「23 人」變成 21 人、「首單成功 5 人」變成 4 人（116、246、255、256）、「首單失敗 4 人」變成 3 人（22、102、258）。是否重算請暴君裁定。
4. `biz_api_key` 現有 26 位持有者 / 38 把 key（含 4、82、117）；spec 的「23」是扣掉名單後的數，一致。
5. 記憶 price-no-change-0928 未被觸碰：本次未改任何定價，只新增遙測。

## 對後續的意義（一句話）

真正的瓶頸是**「建了 key 卻從沒發起第一次調用」**（14/23，且 9 人額度充足），不是鑑權失敗。S1 的 `api_rejection` 從下一筆請求起才能把「未發起」與「發起被拒」分開；在此之前，任何 401/402 佔比都是猜測。
