## 2. 形而上：系统相信了四件错的事

这是第一性原理层面的判断，不是补丁清单。每一层都先给"系统实际信什么"，再给"形而下发生了什么"。

### 层次一（本体论）：把"工作"实现成"运行/事件"

系统把用户的目标（一首歌、一支片、一份歌词）表示成模型会话、子代理 run、工具调用事件。于是"停止""取消""完成"都作用在运行上，而工作量、外部副作用、交付义务并不随运行结束。

- 形而下 1：用户停止后真实扣费与产物仍存在——`READER-BRIEF` 证据 `pack-0001/contradiction`（评审 stopped，仍有 3057 字部分产物）；HANDOFF 记录 b857 取消后真实扣 1 币。
- 形而下 2：子代理被 soft-stop 后，编辑席位的 v6 从未产出，交付文档却继续写 v6 时长——`pack-0002` `recon:50680768`、`recon:016cc788`。
- 代码草案（job-store `generationWorkControl` / `startGenerationReceipt`）方向正确：把"可提交"绑定到耐久工作记录而非模型运行。但尚未行为验证。

### 层次二（认识论）：把"发出调用"当作"完成"

系统允许 `running` 成为模型世界的合法状态，也允许模型用"已提交/已受理"替代"已交付"。

- 形而下 3：**53.3% 工具无回执**（上表），模型据此继续推理，用户拿到的是话术。
- 形而下 4：`已受理 ≠ 已出图 ≠ 已落盘` 被同一个子代理自己写在回执里（`pack-0009` `recon:196ad0a6`），但主流程仍按"已受理"上报进度。
- 形而下 5：604 条矛盾中最高频的形态是"对外说完成、回执说 queued/空"（`pack-0015` `ef07ba15` 6/6 实则 0 落盘；`pack-0021` `2596ecee` 图已出 0/8 落盘）。
- 缺口（草案未覆盖）：**工具生命周期没有终态收敛**。running 超时后应变成 `unknown/expired` 并由网关向模型与用户同时播报，而不是永久 running。

### 层次三（权威论）：把规则写在提示词里，当作已执行

幂等、授权、诚实、评审独立性、禁止重复生成，全部以"提示词要求"存在；执行点在工具入口。

- 形而下 6：声明"已停手"后同一转录继续提交 3 张图（`pack-0002` `recon:12693c7f`）。
- 形而下 7：73 秒前裁决"一次都不要提交"，随后自行宣称"网关持续授权"派出 1 币生成（`pack-0112` `tool:b039cc11` vs `tool:26d72bcc`）。
- 形而下 8：评审席没有 write/shell，报告无法落盘却给出 PASS/PARTIAL（`pack-0011` `recon:408240b7`；`pack-0095` `tool:2ea7f3b8`）。
- 草案已把"问题超时/跳过不等于授权"改成 fail-closed（`questions-gw`/`timers-gw`/`messages-gw-admission`），这是把权威从提示词搬到代码，方向正确。

### 层次四（状态论）：工程状态没有单一真源

画布、会话上下文、工具回执、账本各是一份"真相"，互相覆盖或互相冒充。

- 形而下 9：旧标签页整份覆盖新快照、agent 写穿被吞（草案 `canvas-cascade-state` 的 CAS+rev 正是为此）。
- 形而下 10：压缩摘要把 `applied:6` 记成 dry_run，把失败写成"已成功提交"（`pack-0073` `message:b289f64a`；`pack-0087` `message:196a893b`）。
- 形而下 11：纯文字任务被画布写穿闸逼着写画布（`pack-0043` 31 个工具全空仍被要求写穿；`pack-0046` 画布读 12 次全空）。这一条与 HANDOFF 记录的 4665094d/a494113e 修复一致，但证据显示闸门本身仍在制造空转。

## 3. 对现有 12 文件草案的独立判断

只按"证据是否支持"判，不按作者是谁。

**有证据支持、可以保留**：

1. `job-store.ts`：工作控制版本 + 提交前 claim-once。直接对应形而下 1/6/7（取消后仍提交、重复提交 2,790 组）。
2. `questions-gw.ts`/`timers-gw.ts`/`messages-gw-admission.ts`：跳过/超时不再当授权，拒绝未确认则保留问题卡。对应"问用户不构成批准"。
3. `canvas-cascade-state.ts`：rev 随快照持久化、CAS 拒绝无版本写入、`committed/render_pending` 分离。对应形而下 9/10。
4. `session-read.ts`：停止时把 `future_submissions` 与 `upstream_cancelled/refunded` 分开播报。这是"不欺骗"的最低形态。
5. `subagent-runs.ts`：停子代理时撤销其未来提交，但保留已提交任务的责任链。方向正确。

**证据不足、属于推演或高风险**：

1. `messages-gw-admission.ts` 用正则从用户消息识别"取消/恢复"。证据里没有一条证明该正则覆盖面足够；误判（例如"不要生成歌曲，只要歌词"）会把正常任务标成取消。这是把权威从提示词搬到正则，仍然是猜测。需要显式控制位（按钮/命令）作为主通道，文本只作辅助。
2. `canvas-cascade-state.ts` 的 rev 以 `Date.now()*1000` 起步并且要求 CAS 严格相等：老客户端/首写路径若没带 rev 会全部 409。草案同步改了前端 `rev ?? 0`，但跨端（小程序/桌面桥）是否都升级未验证。
3. `persistSessionNow` 在每次画布写入时同步落盘；VPS 2 核、磁盘已紧张，尚未测吞吐。
4. `sessions-core.teardownSession` 现在会 `clearCanvasState`：若 teardown 发生在恢复路径，可能把仍在内存的画布工程丢掉。证据未覆盖。

**结论**：草案可以作为下一轮修复的起点，但不能当成"已修好"。没有一条经过真实会话回归。

## 4. 三阶段治理：删 → 简 → 加速 → 自动化

马斯克式顺序：先删掉不该存在的，再简化，再加速，最后才自动化。不要把顺序倒过来加提示词。

### 删（不做也能活的东西）

1. **删掉"纯文字任务必须写画布"的闸**。证据：`pack-0043`（31 次空工具仍要求写穿）、`pack-0046`（12 次画布读取全空）。已有 4665094d 的部分修复，但闸门仍应按"是否需要可编辑工程"判定，而不是按"是否多步影音"。
2. **删掉"跳过问题=同意"的语义**（草案已做），以及"超时自动代答"的默认路径。
3. **删掉把 `running` 当状态上报的 UI/正文**。世界上不存在"正在跑且永远不结束"的工具；超过阈值必须是 `unknown`。

### 简（一个真源，一条责任链）

4. **一个耐久工作记录**：`generation_receipts` 作为唯一工作真源，会话/子代理只是执行者；画布、账本、通知都从它派生。草案的 `intent_version` 是第一步。
5. **一个画布版本令牌**：服务端 rev，所有端只带 rev，不再出现"缺版本=接受"。
6. **一个交付判据**：`delivered = artifact(真实可取用) + receipt(成功) + version(当前交付版)`。三者缺一，正文不得出现"已完成/已交付"。

### 加速（让等待变短，而不是让人等）

7. **提交即返回 task_id，结果走收件箱**：证据显示大量时间花在轮询/等待/重复探测（`pack-0075` 第 20 次重投间隔 12,302 秒；`pack-0116` 声称放弃但 bash 仍 running）。
8. **孤儿任务回收**：53.3% 的 running 单元里有相当部分是上游已结束、网关未收尾。收件箱按 producer 归属回收，不依赖原会话活着。

### 自动化（把纪律变成代码）

9. **工具生命周期闸**：`running` 超过 T 秒 → `unknown`，向模型注入"未确认，不得假设成功"；同一 `(tool,input)` 在 pending 期间重复调用直接返回原 task_id。
10. **交付闸**：turn 结束前校验 `delivered` 三要素；不满足则拒绝 `turn.done` 并给用户明确的失败态（不是再写一句提示词）。
11. **席位能力预检**：派工前校验该席位工具表是否包含任务书要求的工具（editor 无 `image_generate` 的证据：`pack-0002` `recon:6f97202c`、`pack-0005` `recon:b0626a59`）。缺工具不应到子代理运行 10 分钟后才暴露。
12. **评审证据闸**：评审结论必须绑定被审 artifact 的 hash/URL 与工具回执；`PASS` 与 `PARTIAL/FAIL` 不得并存交付。
